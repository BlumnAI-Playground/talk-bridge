같은 상담 화면을 서로 다른 연결 방식으로 구현해, 파트너가 자기 상황에 맞는 것을 골라
그대로 베껴 쓸 수 있게 하는 것이 목적입니다.

각 샘플은 독립 실행됩니다. 원하는 디렉터리로 들어가 그 안의 README 를 따르세요.

## 왜 방식이 나뉘는가 — 수신을 어떻게 받을 것인가

발신(내가 고객에게)은 어느 방식이든 똑같습니다. HTTPS 요청 한 번이면 끝입니다.
**갈리는 지점은 수신(고객이 나에게)입니다.** 카카오에서 출발한 메시지가 내 코드까지
도달하는 마지막 한 구간을, 누가 어떻게 뚫느냐가 다릅니다.

### 01 — CLI × 게이트웨이 : 내가 나가서 받아온다

```
카카오 → TalkBridge 서버
                │
                │  ← 내 PC 가 밖으로 나가서 연결(SSE)
                │     방화벽 안에서도 그대로 열린다
         talkbridge gateway (내 PC 데몬)
                │
                │  webhook sink: http://127.0.0.1:8787/webhook
                ▼
           내 앱 (localhost)
```

게이트웨이 데몬이 **내 쪽에서 밖으로** TalkBridge 에 붙습니다(아웃바운드 SSE).
받은 이벤트는 데몬이 localhost 로 넘겨줍니다. 외부에서 내 쪽으로 들어오는 연결이
아예 없으므로, 준비할 것이 사라집니다.

**필요 없는 것:**

- ❌ 공인 도메인 · DNS A/CNAME 레코드
- ❌ TLS 인증서 발급·갱신 (Let's Encrypt, 인증서 만료 감시)
- ❌ 인바운드 방화벽 규칙 · 포트 개방 · 공인 IP
- ❌ 리버스 프록시(nginx·Caddy) 설정
- ❌ 개발용 터널(ngrok·Tailscale Funnel)
- ❌ 로드밸런서 · 보안그룹 · NAT 홀펀칭

**그래서 이런 경우에 맞습니다:**

- 사내망·VPN 안에서만 도는 상담 시스템 (외부 노출 자체가 금지된 환경)
- 노트북에서 바로 띄워 보는 검증·데모 — `npm start` 하나로 끝
- 인프라 담당자를 거치지 않고 개발자 혼자 붙여야 하는 상황
- DNS 변경에 결재·리드타임이 걸리는 조직

**대신 감수하는 것:**

- 데몬이 **살아 있어야** 수신됩니다 (프로세스가 죽으면 그동안의 이벤트는 재기동 후 재생)
- 재시도가 **인메모리 경량**입니다 — 1s → 3s, 최대 3회. 영속 재개 없음
- 상시 가동 서버가 필요하면 그 서버에서 데몬을 돌려야 합니다

### 02 — API × 실제 웹훅 : 상대가 나에게 찾아온다

```
카카오 → TalkBridge 호스티드 게이트웨이
                │
                │  ← TalkBridge 가 내 쪽으로 들어온다
                │     공인 HTTPS 주소가 있어야 도달한다
                ▼
     https://hook.mycompany.com/webhook
```

TalkBridge 서버가 **내 공개 엔드포인트로 직접** POST 합니다.
그래서 위에서 "필요 없는 것"으로 적은 항목들이 전부 **필요해집니다** —
공인 도메인, DNS, TLS 인증서, 인바운드 방화벽 허용. 사설 IP 로는 전달되지 않습니다
(SSRF 차단). 로컬 개발이라면 터널이 있어야 합니다.

**대신 얻는 것:**

- 전달 원장이 **영속**됩니다 — 게이트웨이가 재기동해도 미완료 전달을 재개
- 재시도가 5회로 넉넉합니다 — 1s → 5s → 30s → 2m → 10m
- 내 프로세스가 잠깐 죽어도 이벤트가 유실되지 않습니다
- 서버측 dedupe 가 있습니다
- 중간에 데몬이 없으니 관리할 프로세스가 하나 줄어듭니다

**그래서 이런 경우에 맞습니다:** 상시 가동되는 프로덕션 서비스, 유실이 곧 손실인 상담 운영.

### 03 — 01 + 상담지식 그래프 : 과거 상담을 그래프로 찾는다

01 을 **손대지 않고 복제**한 뒤, CLI 에 내장된 상담지식 온톨로지(그래프)를 **미리 만들어진 Cypher 조회 10종**으로
탐색하는 패널을 붙였습니다. 수신·발신·서명은 01 과 같습니다. 그래프는 `고객 → 문의 → 응답 → 언급 단어` 이며,
**톡브릿지 상담센터에 파트너 개발자들이 CLI·API 연동을 문의하는 18건**의 데모 데이터(`npm run demo:seed`)로 바로 살펴볼 수 있습니다.
AI(자연어 검색·LLM 엔티티 추출)는 쓰지 않습니다 — 다음 샘플에서 다룹니다. 그래프가 필요 없는 파트너는 01 을 그대로 쓰면 됩니다.

> **위치**: 톡브릿지 CLI 로 **상담 Agent 기능을 확장**하고자 할 때 활용할 수 있는 샘플 — 톡브릿지가 부가 기능인 **상담 분석 Agent** 로 확장되는 모습을 보여주는 **데모성 구현**입니다.
> 그래프 기능은 상담 내역을 활용한 온톨로지 구축에 참고할 수 있는 연구 샘플이며, CLI 가 파트너사의 온톨로지를 위해 공식 제공하는 기능은 아닙니다.
> CLI 가 설치된 곳에서 **온디바이스로 라이트웨이하게 로컬 실험**을 할 수 있고, 실 운영에서는 규모에 맞는 그래프 DB 로 **별도 구축·운영을 권장**합니다.

[![03 상담지식 온톨로지 그래프](03-cli-knowledge-graph/docs/screenshot-graph.png)](03-cli-knowledge-graph/#talkbridge-cli--그래프-확장편)

> CLI **v1.1.0+** 가 필요합니다 — 게이트웨이가 떠 있어도 조회 API 를 경유해 조회되고, `--json` 으로 여러 컬럼을 그대로 받습니다.
> 쓰기(데모 적재·`build`)만 게이트웨이를 잠시 멈췄다 켭니다. v1.0.0 시절의 제약과 해소 과정은 [03 README §5](03-cli-knowledge-graph/README.md#5-v100-의-두-제약과-v110-에서의-해소) 에 있습니다.

## 어느 쪽을 고를까

| 질문 | 예 → 01 CLI | 아니오 → 02 API |
|---|---|---|
| 공인 도메인을 새로 뚫는 데 결재·리드타임이 필요한가? | ✅ | |
| 사내망·VPN 안에서만 돌아야 하는가? | ✅ | |
| 지금 당장 노트북에서 검증부터 하고 싶은가? | ✅ | |
| 24/7 무중단 운영이고 이벤트 유실이 곧 손실인가? | | ✅ |
| 이미 공개 API 서버를 운영 중인가? | | ✅ |

**둘은 갈아탈 수 있습니다.** brandKey·userKey·kind·seq 라는 도메인 모델과
서명 스킴(`v0:ts:rawbody` HMAC-SHA256)이 양쪽에서 동일하기 때문에,
수신 핸들러 코드는 그대로 두고 **누가 전달하느냐만** 바꾸면 됩니다.
01 로 검증하고 02 로 승격하는 경로가 자연스럽습니다.

> 실제로 02 는 01 의 `server/signature.js`·`store.js`·`sse.js` 를 **바이트 단위로 그대로** 쓰고,
> `server/webhook.js` 는 본문 조회 **두 줄**(import + 호출, CLI → REST)만 바꿨습니다. 바뀌는 것은
> "게이트웨이를 내가 띄우느냐, 톡브릿지 센터가 띄우느냐" 와 "조회를 CLI 로 하느냐 REST 로 하느냐" 뿐입니다.

## 공통 전제

모든 샘플이 아래를 공유합니다.

- **Node.js 18+**, 외부 의존성 없음
- 프론트는 **바닐라 JS** (프레임워크·번들러 없음)
- 카카오 채널이 TalkBridge 에 연결돼 있고 상담이 활성화된 상태
- 발신은 **활성 세션에만** 가능하고 **상담 건수를 소진**합니다 (조회·설정은 비과금)

### 공통 도메인 모델

| | 설명 |
|---|---|
| `brandKey` | 브랜드(=카카오 채널) 키. 모든 호출의 스코프 |
| `userKey` | 고객 상관키. **수신에서 받은 값을 그대로 발신에 쓴다** |
| `seq` | 브랜드 저널 단조증가 시퀀스. 순서·멱등 판단 기준 |
| `kind` | `message` · `agent` · `reference` · `expired` · `ended` |

### 어느 샘플에서든 지켜야 하는 것

1. **서명은 raw body 로 검증** — 파싱 후 재직렬화하면 깨집니다
2. **정상 처리는 무조건 2xx** — 4xx 도 재시도 대상입니다
3. **즉시 2xx 후 비동기 후처리** — 게이트웨이 타임아웃 회피
4. **`X-Bridge-Delivery-Id` 로 멱등** — at-least-once 라 중복이 옵니다
5. **`kind: "agent"` 는 내 발신의 echo** — 자동응답에서 거르지 않으면 무한 루프
